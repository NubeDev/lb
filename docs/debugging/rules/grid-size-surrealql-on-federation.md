# `grid.size()` emits SurrealQL against a federation source — and takes `ai.classify` down with it

**Area:** rules (grid) / ai verbs / federation
**Date:** 2026-09-08
**Symptom:** any rule calling `.size()` on a grid over a **federation** source (sqlite/postgres) fails:

```
rejected sql: parse error: sql parser error: Expected: end of statement, found: GROUP at Line: 1, Column: 71
```

The reported column is past the end of the author's own SQL, so it reads as a bug in *their* query. It
is not — the SQL in the error was generated by `size()`.

## Root cause — one line of SurrealQL on a path that may be DataFusion

`crates/rules/src/grid.rs::size()`:

```rust
let g = self.wrap(format!("SELECT count() AS v FROM {} GROUP ALL", self.subquery()));
```

`count()` (no argument) and `GROUP ALL` are **SurrealQL**. They are correct on the platform/store path
and are not SQL. Every federation source goes through DataFusion, whose parser rejects both — so the
failure is 100% reproducible on sqlite/postgres and invisible on the store.

Verified on a live node, same rule shape, only the source changed:

| Source | `query(...).size()` |
|---|---|
| `store` (platform) | **2** — works |
| `bas-readings` (sqlite federation) | **parse error at `GROUP`** |

## The blast radius is bigger than `size()`

**`ai.classify` is completely unusable on any federation source**, because `size()` is the first thing
it calls — the over-large-grid guard that runs *before* charging the meter
(`crates/rules/src/verbs/ai.rs::classify`). So the failure lands on the author as a SQL parse error
from a verb they called with no SQL at all.

That matters beyond a broken helper. `ai.classify` is the verb best suited to the
"rule decides, model renders" pattern (rubix-ai `rules-calling-ai-scope.md`): bounded rows in, one
label per row out, no set logic asked of the model — exactly the shape a small local model handles
reliably where free-form reasoning fails. And time-series **live in federation sources**, so on the
BAS/FDD path — the one that would use it — it never works.

`columns()` is fine (it uses `head(1)`, plain SQL). `head()` is fine.

## The fix — THREE bugs, one root, found by peeling

There is no spelling both dialects accept. The obvious one-liner (`SELECT COUNT(*) AS v`, no
`GROUP ALL`) fixed federation and **broke the store**: SurrealDB answers
"Unexpected token `*`, expected an expression". Verified in both directions before settling on
dispatch. `SourceKind` is already on the grid — the module doc even says "the grid carries its
`SourceKind` so a…" — the dispatch was simply never made.

Fixing the SQL then exposed the next layer, and that one twice:

1. **`size()` emitted SurrealQL on every source** → parse error on federation. *Dispatch on
   `SourceKind`.*
2. **`size()` read the count with `r.get("v")`** → the federation seam returns column-aligned
   **arrays** (`[3]`, not `{"v":3}`), so it silently returned **0**. A wrong answer, not an error —
   and for `ai.classify`'s over-large-grid guard, "0 rows" means *always under the cap*, defeating the
   guard entirely. *Read both row shapes.*
3. **`ai.classify` built its output with `as_object_mut()`** → `None` on an array row, so the label
   was dropped and the verb returned the **unlabelled rows**. Again a wrong answer, not an error.
   *Normalize with `row_to_map` first — the same normalizer `records()` uses.*

All three are the same root: **the federation row shape was handled in `records()` and nowhere else.**

Verified live after the fix, on one node, same rule shape:

| Case | Before | After |
|---|---|---|
| `size()` platform | 5 | **5** (no regression) |
| `size()` federation, `LIMIT 3` | parse error | **3** |
| `size()` federation, all rows | parse error | **1152** (matches `SELECT COUNT(*)`) |
| `ai.classify` on federation | parse error → then unlabelled rows | **labels land, and are correct** |

The `ai.classify` result is the one that matters: given the flatlined sensor and its healthy twin, the
local 8B model labelled `meter-020-zt` → `frozen-sensor` and `meter-021-zt` → `healthy-sensor`, in one
metered call (8 tokens). That is the verb the "rule decides, model renders" pattern most wants, and it
had never once worked on time-series data.

**The missing test, and it is the whole lesson: exercise every grid method on BOTH seam kinds.** This
survived because grid coverage runs on the platform path, where the SurrealQL is correct and the rows
are objects. A single `size()` test against a sqlite source fails immediately.

## The lesson

**A seam with two backends needs its helpers tested on both, or the helper silently becomes
platform-only.** `records()` documents this exact hazard right below the broken function — it
normalizes object-rows (store) against array-rows (federation) precisely because the two seams differ
— and `size()`, a few lines up, hard-codes one dialect *and* one row shape. The awareness was present
in the file, one screen away, in prose. The coverage was not.

**And note which failures were louder.** The dialect bug threw a parse error and got found. The two
row-shape bugs returned a plausible wrong value — `0` rows, unlabelled rows — and would have sat there
indefinitely, defeating a guard and silently no-op'ing a verb. **A wrong answer is more expensive than
a crash**, and both of these were one `unwrap_or_default()`-shaped decision away from being loud.
