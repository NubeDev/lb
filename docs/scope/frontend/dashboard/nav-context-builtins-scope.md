# Dashboard scope — nav-context built-ins (`${__nav.*}`, `${__page.*}`)

Status: **scope (the ask)**. Promotes to `doc-site/content/public/dashboard/dashboard.md` on ship.

**Owning repo: `lb` — CONTRACT ONLY.** This doc extends the *documented, versioned* built-in namespace
that [`widget-config-vars-scope.md`](widget-config-vars-scope.md) owns, and adds two small typed carriers
so an **extension** or any other client can populate the namespace over the wire. The *resolution* stays
client-side, exactly as
[`dashboard-variables-advanced-scope.md:95`](dashboard-variables-advanced-scope.md) pins it
(*"client-side resolution + interpolation; `either`, no role branch"*). The consumer build is
`NubeIO/rubix-ai → docs/scope/frontend/dashboard/nav-context-vars-scope.md`, which bumps to the
`node-v*` tag this ships in.

A generated page's heading is a lie today. A `modbus`-managed board titled
*"Socomec COUNTIS P44 — energy meter"* renders that one string for every device the ext generated it for,
while the sidebar entry beside it already says `Socomec RTU / test`, the URL already says
`?var-network=socomec-rtu&var-device=test`, and the nav tree already knows the item's parents. The
board's own **panel titles** interpolate (`$point — readings` works), but the **heading**, the
**description**, and the **breadcrumb leaf** do not — so the one string a user reads first is the only
one that cannot say which thing they are looking at. The information exists; there is no *name* for it.

This scope gives it a name. It adds a **nav-context built-in namespace** — `${__nav.label}`,
`${__nav.parent.label}`, `${__nav.path}`, `${__page.title}`, `${__page.ext}` — to the same
`VarScope.builtins` map that already carries `${__user.login}` and `${__workspace}`, resolvable through
the **same interpolation engine, same grammar, same format hints, same unknown-stays-literal rule**. No
new syntax, no second templating system, no server-side expansion. And it makes the two carriers that
feed it typed on the record so a non-rubix-ai client, a pack, or an extension gets the same behaviour.

## Goals

- **G1 — A documented built-in namespace for nav/page context.** Extend the built-in list in
  [`widget-config-vars-scope.md`](widget-config-vars-scope.md) §Built-ins with a closed set:

  | Reference | Meaning |
  |---|---|
  | `${__nav.label}` | The label of the nav item the viewer arrived through — verbatim, as the sidebar renders it. |
  | `${__nav.parent.label}` | The label of that item's parent node (the collapsible section / group). |
  | `${__nav.parent.parent.label}` | Grandparent. **Key omitted** above the tree root ⇒ reference stays literal. |
  | `${__nav.path}` | The chain **including this item**, joined by ` / ` — `Modbus / Socomec RTU / test`. |
  | `${__nav.id}` | The nav item's slug (`NavItem.id`), stable across relabels/i18n. |
  | `${__page.title}` | The dashboard record's `title` — the un-overridden name. |
  | `${__page.id}` | The dashboard id (alias of the shipped `${__dashboard}`, spelled in the new namespace). |
  | `${__page.ext}` | The `managedBy` extension id — **empty string** on a hand-authored board. |

  **Omitted-vs-empty is decided per key, and the two renders are opposites** — an omitted key leaves the
  reference literal (`${__nav.label}`), an empty-string key erases it. The rule: a key is **omitted**
  when the context is *unknown* (no nav path, above the root — the reference is unresolved and should
  say so), and **empty** when the context is *known to be absent* (`__page.ext` on a hand-authored
  board — the author wrote "generated by ${__page.ext}" and means nothing, not raw braces). Rendering
  `${__page.ext}` literally forever on every hand-authored board would be the wrong answer. The consumer
  scope's table matches this one key-for-key.

  Names live under the **existing `__` built-in prefix**, so `parse.ts:isBuiltinName` already classifies
  them, `validateVariables` already refuses a user variable that would shadow them, and `varUsage.ts`
  already excludes them from "used by N panels". Dotted names already parse — `NAME` is
  `[A-Za-z_][\w.]*` precisely because `${__user.login}` needed it.

- **G2 — Heading, description and crumb are interpolated surfaces.** Declare in the contract that
  `Dashboard.heading`, `Dashboard.description`, `Cell.description` and a row cell's title are
  **template strings** resolved against the page's `VarScope`, on the same terms as a panel title. This
  is a doc/contract change in lb; the render change lands in rubix-ai. lb stores them raw and expands
  nothing — same posture it holds for `Action.argsTemplate`.

- **G3 — `NavItem.label` becomes a template — *non-breaking*.** `ext-loader`'s `NavItem.label`
  (`rust/crates/ext-loader/src/manifest.rs:258`) and `nav/model.rs`'s `NavItem.label` may contain
  `$var` / `${…}` references. The host keeps relaying it **verbatim** — the shell interpolates at render
  against the item's own `vars` binding plus the built-ins. This is what lets an ext write
  `label = "${device}"` on a `dynamic` child and get the device name in the rail *and*, through
  `${__nav.label}`, in the board heading it links to.

  **This is retroactive, so `label` is never hard-rejected.** A shipped manifest may already carry a
  literal `$` — `"Cost $USD"`, `"$/kWh"` — and there is **no escape sequence in the grammar** (no `$$`;
  verified absent from `interpolate.ts` and `parse.ts`). Hard-failing those manifests on a node bump
  would be a breaking change in a scope that claims none. So: `validate_nav` **warns** on an unbound
  reference in `label` and loads the extension anyway; the label renders literally, exactly as it does
  today. Only `title_template` — a **new** field, so nothing can already contain one — is hard-rejected
  (§G4). The same retroactivity applies to every already-stored `heading` / `description` /
  `Cell.description` containing a `$`; §Testing pins an explicit existing-data case.

  **Named upstream ask (not this scope):** the grammar has no way to write a literal `${`. Adding `$$`
  is a change to the **frozen** engine that `widget-config-vars-scope.md` owns (`interpolate.ts`,
  `parse.ts`, `interpolateValue.ts`, `varUsage.ts` and the Grafana bridge all agree on the current
  regex), so it belongs in that scope, not this one. Recorded here so the next person does not
  re-derive it: `"\\$\\$" → "$"`, applied in `interpolate` before the reference scan, with
  `extractVarNames` taught to skip an escaped `$`.

- **G4 — The two typed carriers.** So the namespace has something real to resolve from on any client:
  - `NavItem.title_template: Option<String>` on **both** `nav/model.rs` and `ext-loader`'s manifest — an
    optional heading override the item pins on the board it opens, folded into the viewer's context
    alongside the existing `vars` map. This is the field an extension sets when it wants the *board*
    named from the *nav item* without every board carrying `${__nav.label}` in its heading.
  - `Dashboard.heading` / `.description` gain a doc-comment stating they are templates (no type change —
    they are already `Option<String>`, so **no wire break, no migration**).
  - `ResolvedItem` (`nav/resolve.rs`) carries `title_template` through to the client next to `vars`, so a
    `template-group` fan-out (`resolve_template_group.rs`) gives each generated item its own heading.

- **G5 — Zero server-side expansion.** The host never substitutes. `access_check.rs`'s required-var
  preflight, `pack/apply.rs`, the Grafana import/export bridge and `dashboard_save` all keep treating
  these strings as opaque. The only new server behaviour is **validation** (§How it fits).

- **G6 — Grafana import/export stays lossless.** Grafana has no nav-context equivalent, so on export the
  strings ride out as-is (a `${__nav.label}` in a Grafana JSON is simply an unknown variable, which
  Grafana also leaves literal — the round trip is byte-stable in both directions).

## Non-goals

- **No server-side templating engine.** No `${…}` expansion in Rust, ever, for user variables. The two
  existing macro layers (`viz/macros.rs` value macros, `federation/sql_macros.rs` function macros) are
  time/interval only and stay that way. Interpolating a heading server-side would need identity, the
  live URL range and the viewer's caps at render time — none of which the store layer has, and all of
  which the client already holds.
- **No new reference syntax.** No `{{…}}`, no expression language, no `+` concatenation, no method calls.
  The ask sketched `${parent.parent.name + parent.name + "something"}`; the answer is
  `${__nav.parent.parent.label} ${__nav.parent.label} something` — plain-text concatenation *by writing
  plain text*, which is how every existing template in the system already composes. Adding an expression
  evaluator would fork the grammar `parse.ts`, `interpolate.ts`, `varUsage.ts`, the Grafana bridge and
  the SQL-macro layers all agree on today, for zero capability the literal form lacks.
- **No `parent` field on an extension's nav item.** An extension still cannot nest itself under a host
  group (`ext-nav-contribution-scope.md`). `${__nav.parent.label}` reads the tree the shell *built*; it
  does not let an ext choose its place in it.
- **No identity or caps leakage.** `${__nav.*}` is presentation context. It is never a gate input, never
  reaches `access_check`, and a widget cannot use it to reach data its caps deny.
- **No nav labels resolved from the store.** `${__nav.label}` is the *label the viewer navigated
  through*, taken from the resolved nav payload. It is not a lookup.
- **No report/PDF change.** Report export stays client-driven snapshots (`report/export.rs` takes no
  vars); the heading a report captures is whatever the client rendered, which is now the interpolated
  one for free.

## Intent / approach

**One namespace, one engine, two typed carriers.**

The whole design rests on a fact the survey made plain: `VarScope` is `{ values, builtins }`, and
`interpolate()` already falls through to `builtins` for any `__`-prefixed name. So a nav-context
built-in needs **no engine change at all** — it is a matter of the shell putting more keys in the map it
already builds, and of `lb` writing down which keys are guaranteed to be there. That is why this scope's
lb footprint is mostly a contract: the code that would have to change already does the right thing.

The two carriers exist for the "other clients" half of the ask. Without them, `${__nav.label}` resolves
only in rubix-ai's shell, from rubix-ai's client-side nav tree. With `NavItem.title_template` on the
manifest and on `nav/model.rs`, and with the guarantee that `ResolvedItem` relays it beside `vars`, any
client that consumes `nav.resolve` and `ext.list` gets the same three things over the wire: the label,
the parent chain (`items` is already recursive), and the per-item heading override. The namespace is then
a *client-side rendering of a server-supplied context* — which is the same shape `${__workspace}` already
has.

**Validation is the one genuinely new server behaviour — and it must not be manifest-only.**
`validate_nav` (`manifest.rs:~65`) gains a check that a template references only names the item can
actually bind: its own `vars` keys, the declared `var` of a template group, or a known built-in. A
`title_template` violation is a **hard reject** with the offending name in the message (it is a new
field, so nothing can already break); a `label` violation is a **warn** (§G3 — retroactivity).

**The same validator must run on the nav-builder write path, not just on manifest load.** A nav item
created through the nav API (`nav/model.rs`, the `nav.save` path) is the *other* way an item comes into
existence, and validating only the extension route would mean an ext-authored template is checked and
length-capped while a hand-authored one is neither. That asymmetry is precisely what **rule 10** exists
to catch — the core would be treating the extension seam as the privileged path. So the check lives in
one shared function in `nav/`, called from both, and **host nav items carry `title_template` too**,
with the same 256-char cap. An extension can name a board from its manifest; a workspace admin can name
one from the nav builder. Same field, same validator, same cap.

The consumer's authoring surface is deliberately **softer** than the server's: rubix-ai's Page-settings
dialog shows an unresolved-reference note and **still saves** (matching `VariableEditor`'s shipped
save-anyway posture). That asymmetry is intentional and stated in both docs — a manifest is loaded once
by a machine and a bad template there is a deploy-time defect worth failing on, whereas a human editing
a heading mid-thought must never be blocked by a reference they are about to finish typing.

**Rejected — a `heading_resolved` field the host computes and stores.** It would be wrong the instant a
second viewer opened the board with a different `?var-`, would have to be recomputed on every variable
edit, and would put the store in the business of knowing what a viewer selected — which
`model.rs:329-333` explicitly forbids (*"The host stores the DEFINITIONS only; the per-viewer SELECTION
lives in the URL"*).

**Rejected — resolving nav context inside the extension's iframe.** An ext knows its own labels but not
the host tree it was mounted into, and letting it *claim* a parent chain would make `${__nav.*}` as
spoofable as a client-supplied `${__user.login}`. Same reasoning that put `resolveBuiltins` shell-side in
the first place (`widget-config-vars-scope.md:107`).

## How it fits

**Isolation / tenancy.** Nothing crosses a workspace. `nav.resolve` is already workspace-scoped and
caps-gated; `title_template` rides the record it is stored on. A `${__nav.*}` value is derived from a
payload the caller was already allowed to read.

**Capabilities & the deny path.** No new caps. Nav-context built-ins are **presentation only** and must
never reach a gate: a widget that interpolates `${__nav.label}` into a query argument sends a *string*
through the normal `mcp:<tool>:call` wall, and the wall does not care where the string came from. The
required-var preflight (`access_check.rs:218-226`) is untouched — a built-in is never `required`.

**Placement.** `either`, no role branch. The carriers are store fields; the resolution is client-side.
An embedded node and the stock binary behave identically.

**Rule 10.** Nothing here names an extension. `${__page.ext}` reads `managedBy` — a *generic* provenance
field the host already stores for any managed board — the way `ManagedBadge` already does. `modbus`
appears nowhere in lb.

**API / MCP surface.** No new verbs. `dashboard_save` / `dashboard_save_meta` already carry `heading`
and `description` in `PageMeta` (`save.rs:91`). `nav.resolve`'s `ResolvedItem` gains one optional string.
`ext.list`'s `ExtUi.nav` items gain the same. Both are additive `Option<String>` / omitted-when-absent, so
an older client ignores them and an older node returns `None` — **no tag coordination beyond the bump**.

**Data.** Additive only. `NavItem.title_template` and the doc-comment changes need **no migration**;
`SCHEMA_VERSION` stays at 3 because `Dashboard`'s shape is unchanged. Existing nav records deserialize
with `title_template: None`.

**Motion / secrets.** None. A template is authored text; it can reference a variable whose *value* came
from a query the author could run, which is the same exposure a panel title already has.

## Example flow

1. The `modbus` extension declares in its manifest:

   ```toml
   [[ui.nav]]
   id      = "socomec-rtu"
   label   = "Socomec RTU"
   dynamic = true              # children published at runtime via bridge.setNav
   ```

   and at runtime publishes a child per device: `{ id: "test", label: "test",
   dashboard: "dashboard:modbus-tmpl-socomec-countis-p44",
   vars: { network: "socomec-rtu", device: "test" },
   titleTemplate: "${__nav.parent.label} · ${__nav.label} — energy meter" }`.

2. `ext-loader` validates the manifest: `validate_nav` confirms every reference in `label` and
   `title_template` resolves against the item's own `vars` keys (`network`, `device`) or the built-in
   namespace. `${__nav.parent.label}` is a built-in ⇒ accepted.

3. The host relays the item **verbatim** through `ext.list` → `ExtUi.nav`. It expands nothing.

4. The shell builds its nav tree (`buildExtGroup`), and the viewer clicks *Modbus → Socomec RTU → test*.
   The shell folds the item's `vars` into the URL — `?var-network=socomec-rtu&var-device=test` — exactly
   as `ext-dashboard-nav-scope.md` already specifies.

5. `resolveBuiltins` now also receives the **nav context**, derived from the **URL**, not from the click
   — the shell resolves which nav node the current `(dashboard id, vars)` addresses and reads its
   ancestor labels and `titleTemplate` from the resolved model. The returned `builtins` map gains
   `__nav.label = "test"`, `__nav.parent.label = "Socomec RTU"`,
   `__nav.path = "Modbus / Socomec RTU / test"`, `__page.ext = "modbus"`.

6. The board's own record has `heading = "Socomec COUNTIS P44 — energy meter"` — but the nav item pinned
   a `titleTemplate`, which wins. The shell interpolates it against the same `VarScope` the panels use
   and renders **"Socomec RTU · test — energy meter"** in the heading block *and* as the breadcrumb leaf.

7. A second viewer opens the same board from a different device's nav child. Same record, same
   `heading`, different `?var-` and different nav context ⇒ a different rendered title. **Nothing was
   written to the store.**

8. Someone pastes the URL to a colleague, who opens it cold — **and it still resolves.** The reverse
   lookup is on the URL's `(dashboard id, vars)` tuple, which the link carries, so the colleague's shell
   finds the same nav node, the same ancestor labels and the same `titleTemplate`. Refresh, bookmark,
   deep link and shared link all behave identically to the click. `__nav.*` is only absent when the URL
   genuinely addresses no nav item (a board reached from the Dashboards manager, say) — and there the
   references stay **literal** per the shipped unknown-variable rule, and the board falls back to its
   stored `heading`. This is why `title_template` is relayed on `ResolvedItem` rather than handed over
   at click time: the client must be able to re-derive it from state the URL already encodes.

## Testing plan

**Mandatory categories.**
- *Capability-deny* — a caller without the nav surface's gate cap gets no `ResolvedItem`, so no
  `title_template` and no nav context. Assert the field never appears in a denied response.
- *Workspace isolation* — a `title_template` written in ws A is unreadable from ws B; `nav.resolve` in B
  returns B's items only.
- *Hot-reload* — an extension reloaded with a changed `[[ui.nav]] title_template` relays the new value on
  the next `ext.list` with no node restart.

**Unit (Rust).**
- `manifest.rs` — `title_template` round-trips TOML → struct → JSON with the camelCase wire name;
  absent ⇒ `None`.
- `validate_nav` — accepts a template referencing a declared `vars` key or a built-in; **hard-rejects**
  a `title_template` referencing an unbound name, with the offending name in the error; rejects over the
  256-char cap.
- **Retroactivity** — a manifest with `label = "Cost $USD"` (a literal `$`, no escape in the grammar)
  **loads with a warning**, does not fail, and relays the label byte-identical. This is the breaking-
  change guard; it fails loudly if someone later tightens `label` to a hard reject.
- The shared validator is reached from **both** the manifest path and the nav-builder write path — same
  accept/reject verdict for the same template through either door (the rule-10 symmetry check).
- `nav/model.rs` — an existing nav record with no `title_template` deserializes (`None`).
- **Projection trap, through the path that actually bites** — write a *plain host* nav record carrying
  `title_template` via the nav API, then read it back through **`nav.resolve`** and assert the value
  survives. The struct round-trip alone would pass while the store `SELECT` silently dropped it; the
  manifest and template-group tests below both bypass that path, so this is the one that catches it.
- `nav/resolve_template_group.rs` — a fan-out emits one `ResolvedItem` per option value, each carrying
  both `vars` and the group's `title_template`.

**Integration (real store, `mem://`, no mocks).**
- Save a dashboard whose `heading` contains `${__nav.label}`; read it back byte-identical. The host
  expanded nothing.
- **Existing data** — a dashboard whose `heading`/`description`/`Cell.description` already contains a
  bare literal `$` (`"Cost $USD per kWh"`) saves, loads and exports **unchanged**, and no validator
  rejects it. Declaring these fields templates must not retroactively invalidate stored records.
- `pack/apply.rs` applies a pack dashboard with a templated heading; the string survives verbatim.
- Grafana export → import round trip with a templated heading and description: byte-stable.
- `dashboard_save_meta` with a heading of only `${__page.title}` — stored as written, not resolved.

**Not tested here.** Rendering, the ` / ` join, the crumb, and the literal-fallback are the consumer's
tests — see the rubix-ai scope's plan.

## Risks & hard problems

- **The projection trap.** `title_template` must be added to the store `SELECT` in `nav/store.rs` as well
  as the struct, or it reads back as `None` silently — the exact failure mode already recorded for
  `queryOptions` / `entity` / `heading` on `Dashboard`. This is the single highest-probability bug in the
  scope, and the test that catches it must go **through `nav.resolve` on a plain host nav record** — the
  manifest and template-group tests never touch the store read path.
- **Retroactive templating of shipped strings.** Declaring `label` / `heading` / `description` templates
  changes the meaning of data that already exists. A literal `$` was legal yesterday and there is no
  escape sequence to rewrite it with. Handled by warn-not-reject on `label` (§G3) plus the existing-data
  test above — but it is the reason this scope can honestly claim "no wire break, no migration", and the
  claim is void if anyone later promotes that warning to an error without shipping `$$` first.
- **Library panels carry nav-context references across boards.** A library panel whose title or
  description references `${__nav.*}` resolves differently on every board that includes it — by design
  (that is what a shared panel with context *should* do), but surprising to an author who wrote it on
  one board. The host stores the ref and expands nothing, so there is no correctness issue here; it is a
  documentation note for `library-panels-scope.md`, not a behaviour change.
- **Label churn breaks a template.** `${__nav.parent.label}` renders the *label*, which an ext may
  re-translate or rename. That is intended (the heading should follow the rail), but an author wanting
  stability should use `${__nav.id}`. Both are offered; the docs say which is which.
- **Depth beyond grandparent.** `${__nav.parent.parent.parent.label}` is not in the closed set. Rather
  than an unbounded chain, `${__nav.path}` covers "everything above me" and the set stops at two levels.
  If a real case needs three, it is an additive key, not a redesign.
- **A cycle via `titleTemplate` referencing itself.** `${__nav.label}` inside a nav item's own `label` is
  self-referential. Resolution order is fixed: `label` is interpolated against `vars` + non-nav built-ins
  only; `__nav.label` is computed *from* the resolved label. `validate_nav` rejects `__nav.*` inside
  `label`.
- **An unbounded template as a DoS.** Capped like every other manifest string (≤256 chars for
  `title_template`, consistent with the existing `label ≤64` / `dashboard ref ≤128` caps).

## Open questions

None blocking. Two calls made for the build, stated rather than asked:

1. **`${__page.id}` duplicates the shipped `${__dashboard}`.** Both ship; `${__dashboard}` is kept for
   Grafana-conversion parity (`grafana-conversion-scope.md:121` maps Grafana's `$__dashboard` to it) and
   `${__page.id}` is the spelling inside the new namespace. Aliases, not two mechanisms.
2. **`${__nav.path}` separator is ` / `**, matching the breadcrumb, and the chain **includes the item
   itself**. An author wanting another separator composes the parts by hand.
3. **Omitted vs empty is per-key, not global** — unknown context omits (stays literal), known-absent
   context renders empty. The table in §G1 is the authority and the consumer's table mirrors it.
4. **`label` warns, `title_template` rejects.** Asymmetric on purpose: one is retroactive, one is new.
5. **`$$` escaping is deferred to `widget-config-vars-scope.md`**, which owns the frozen engine. Until
   it ships there is no way to write a literal `${` — which is exactly why `label` cannot hard-fail.
