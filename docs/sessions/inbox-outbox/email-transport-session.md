## The ask, and what was actually missing

The seam was fully built and booted — a durable outbox effect, `RouterTarget` dispatch on the opaque
`"email"` string, `EmailTarget`, the `EmailProvider` trait, catalog-rendered i18n subject/body. The only
non-test impl was `LoggingEmailProvider`, which logged the send and **acked** it. So an admin invited a
colleague, the invite row was written, the outbox drained clean, and the colleague was never told. No
failed row for an operator to find, because from the outbox's point of view nothing failed.

Deliberately small slice, per the scope: fill the seam, don't build a mail service. Durability, retry,
backoff and at-least-once already belong to the outbox; i18n to `lb_prefs`; routing to `RouterTarget`'s
opaque string. What was missing was one thing — bytes on a wire.

## What shipped

### 1. `lb-mail` — the transport crate (`rust/crates/mail/`)

Over `mail-send` + `mail-builder` (the Stalwart suite), `default-features = false` to drop DKIM
(`mail-auth`), the MD5 SASL mechanisms, and `aws-lc-rs` — `ring` is already the workspace's rustls
provider via `reqwest`, so no second crypto backend and no C build on a zig-only toolchain.

- `send/message.rs` — `MailMessage` → RFC 5322 bytes. An HTML body is **always** paired with a text part
  (`multipart/alternative`), supplied or generated by stripping tags while keeping anchor `href`s inline
  (an invite whose text part loses the accept link is useless). `Message-ID` is **injectable** and the
  caller injects the outbox idempotency key — a stable id across retries lets the *receiving* side
  collapse a duplicate.
- `send/smtp.rs` — one submission: connect, protect, authenticate, `MAIL FROM`/`RCPT TO`/`DATA`. Errors
  classified and redacted on the way out.
- `send/tls.rs` — `implicit | starttls | none`, config-only (never inferred from the port), and
  `starttls` **requires** the upgrade.
- `send/auth/` — `plain.rs` (`MailCredentials`, deliberately **no `Debug`** impl), `xoauth2.rs` (the
  access-token cache), `refresh.rs` (the RFC 6749 §6 refresh-token exchange).
- `error.rs` — `MailError::{Transient, Permanent}` + `redact`.

The receive half lands beside this as `fetch/` when `mail-source-scope.md` builds; the folder split is in
place, and nothing empty was scaffolded.

### 2. An honest permanent-failure path in the outbox

The scope asked for "4xx → `Err`, 5xx → permanent fail, no retry storm". The outbox could not express
that: `Target::deliver` returned `Result<(), String>` and the relay **threw the string away**
(`Err(_reason)`), so every failure was identical — retry five times with backoff, then park with no
recorded reason.

- new `outbox/delivery_error.rs` — `DeliveryError { reason, permanent }`, with `From<String>`/`From<&str>`
  producing the **transient** form so adopting it is a signature change, not a semantic one;
- `Effect` gained `last_error: Option<String>` (`#[serde(default)]`, so existing rows load);
- `mark_failed(.., reason)` records it; new `mark_dead_lettered(.., reason)` parks a permanent failure
  immediately; `mark_delivered` clears it (a delivered row carrying a stale error reads as a failure);
- the relay picks the transition from the target's verdict and logs a permanent one at `warn`;
- `outbox.mark_failed` (the sidecar-driver verb) gained optional `reason` + `permanent`, so an
  out-of-process relay gets the same contract; omitting both is exactly the old behaviour.

`RouterTarget`'s "no adapter registered" stayed **transient** on purpose — an effect for a
sidecar-driven target (`relay_ops`: the driver pulls its own effects and marks them itself) has no
in-process route *by design*, and failing it permanently on the first tick would kill effects that were
never this router's to deliver.

### 3. `SmtpEmailProvider` + `PostmarkEmailProvider`

Both in `host/src/outbox/provider_*.rs`, both behind the unchanged `EmailProvider` trait.

Credentials: the config carries a secrets **path** and an env **name**, never a value, and the value is
resolved **at send time in the effect's workspace** through `lb_secrets::get_workspace` — the same
host-mediated precedence (sealed workspace secret → node env → unset) that `agent/resolve_key.rs`
established. So a ws-A effect can only resolve ws-A's secret, rotation needs no redeploy, and the config
struct is `Debug`-safe by construction (there is a test asserting exactly that).

XOAUTH2 is v1, not a follow-up: Gmail/M365 reject passwords in the general case, and an access token
lives ~an hour, so a transport without refresh works for exactly one hour after setup. The cache is keyed
by a **digest of the refresh token**, so rotating the seal invalidates the bearer minted from the old
grant.

Postmark over SES for the provider-API impl (the scope's open question): simplest transactional API
(one `POST` with a server-token header, no request signing), best default deliverability, and — decisive
— **SES already exposes SMTP submission**, so an AWS-resident host is served by `kind: "smtp"` today
without dragging SigV4 signing or an AWS SDK into a core crate.

### 4. Boot selects the transport by name

`BootConfig::email_transport: Option<EmailTransport>` (`Logging | Smtp(..) | Postmark(..)`), built in the
new `node/src/mail.rs` (the binary boundary, where `LB_MAIL_*` is read). Precedence:
embedder-supplied provider → configured transport → logging.

Two things are deliberate here:

- **Unset is a loud `warn`, not silence.** A node with no mail config still boots and still drains (never
  crash, never strand effects) — but it says `email DROPPED (no transport configured …)`. Silence is what
  let #118 live. `kind: "logging"` chosen explicitly stays quiet.
- **A misconfigured transport is reported at boot**, not at the first invite: `validate()` rejects no
  host, no `From`, `xoauth2` without a token endpoint, and a mechanism with no credential source.

### 5. The HTML half of the message

`invite.email.body_html` added to the `en`/`es` builtin catalogs (two keys, so a translator sees both
halves). `lb_prefs::render` never returns blank — an absent key renders as the **key literal** — so
`catalog_html()` turns that back into `None` and the mail goes out text-only.

## Tests

`lb-mail` (27 green): 14 unit + **7 against a real SMTP server** (a listener on a real socket in
`tests/smtp_server/`, scriptable, which hands back the AUTH line and `DATA` bytes it received) + 6
against a **real HTTP token endpoint**.

The SMTP tests assert bytes on a wire, which was previously unprovable: the exact `AUTH PLAIN` SASL blob;
the exact `AUTH XOAUTH2` framing (`base64("user=…\x01auth=Bearer …\x01\x01")` — getting this wrong is the
whole "supports Gmail" story failing at the last byte); a multipart message **parsed back with
`mail-parser`** (text alternative + HTML part + attachment + an 8-bit subject round-trip + the injected
`Message-ID`); `550` permanent vs `421` retryable; a rejecting relay that **echoes the AUTH blob** and an
error that contains neither the password nor its base64 (the scope's explicit secret-hygiene test); a
hung session timing out; and `starttls` refusing to continue in the clear (asserting the server saw
**no** AUTH line and **no** message).

Token tests: the RFC 6749 grant actually posted; five sends sharing one refresh; an expiring token
re-minted; rotation invalidating the cache; `invalid_grant` permanent vs `503` transient; and a chatty
error body that echoes the submitted secrets producing an error carrying neither.

`lb-host` — new `tests/email_transport_test.rs`, the mandatory categories:

- **capability deny (enqueue side)** — an unauthorized `invite.create` writes **no outbox row at all**
  (not merely an error), and the caller under test holds a *different real* capability so the assertion
  is about the `invite.create` gate rather than "a capless principal is denied everything"; the granted
  path then stages one, so the emptiness assertion cannot be vacuous.
- **workspace isolation** — a password sealed in `globex` is unreachable from an `acme` effect. Observable
  without a relay: acme fails **permanently** with "no credential at secret path …" while globex gets
  past resolution and fails with a **transient** connection error against a closed port.
- the `push_target` hardcoded-workspace regression cross-checked: an effect with no `workspace` is parked
  on the first attempt with a reason, and nothing is sent.
- **offline / re-drain** — a transient failure re-drains and sends exactly once; the reason is on the row
  while it is `failed`, and gone once delivered.
- **honest outcomes** — a permanent failure parks at `attempts: 1` and is not resurrected by a later pass.

`node/tests/relay_boot_test.rs` gained: a node configured with `kind: "smtp"` against an unreachable
relay **boots** and its effect stays **owed** (`failed`, with an `smtp` reason on the row, still returned
by `due`) — the direct inverse of the old behaviour, which acked a send that never happened.

Kept green: `invite_email_relay_test`, `invite_i18n_test`, `relay_boot_test`, `push_deliver_test`.

## The bug the tests found

The timeout test failed on the first run — **after 30 s against a 300 ms timeout**. `mail-send`'s
cleartext `connect_plain()` bounds only the TCP connect and then reads the greeting through an unbounded
`read()`. Since `send_smtp` runs inside the relay tick, a wedged LAN relay would have stalled *every*
outbox delivery behind it, push included. `send_smtp` now owns the bound itself. Full write-up in the
debugging entry.

Also caught by its own test: the access-token cache key started as a length-and-tail fingerprint of the
refresh token, and two same-length tokens sharing a suffix **collided** — a rotated grant silently reused
the old grant's access token, which is the worst failure mode there is (the operator believes the old
token is out of service). Now a SHA-256 prefix; the test fixture keeps the colliding shape on purpose.

## Open questions answered

- **Which API provider first** → Postmark (reasoning above).
- **Node-level vs per-workspace transport** → node-level in v1, as scoped; per-workspace sending
  identities named as a follow-up.
- **Config record vs boot config** → boot config, and the pressure the question anticipated is mostly
  relieved by resolving credentials per send: rotating a *credential* needs no restart. Changing the
  *relay* still does; a stored `mail.transport.*` record remains a named follow-up (it is CRUD with a
  real caller once a per-workspace transport exists).
- **Where the plain-text alternative comes from** → two catalog keys, with a generated fallback.
- **Delivered-marker granularity** → a new outbox-level `outbox/delivered.rs` keyed by
  `(target, dedup_key, recipient)`. `notify/delivered.rs` keeps its own `push_delivered` table for now:
  migrating live push markers buys nothing but a one-time re-send. Consolidating is a follow-up.
- **Container vs listener for the real-SMTP test** → in-test listener for the protocol/auth/MIME/error
  matrix (keeps `cargo test --workspace` self-contained). The docker-gated real-TLS test is **not** in
  this slice — see below.

## Verified against real Gmail

Asked "so will Gmail actually work?", the honest answer at first was "unverified" — every other transport
test runs over **plaintext** against the in-test server, so the TLS paths had no coverage and STARTTLS on
587 is exactly what Gmail requires. Closed with `tests/gmail_reach_test.rs` (`#[ignore]`d, 2 tests, run
on demand): authenticate to `smtp.gmail.com:587` with a deliberately **bogus** credential and assert
Gmail's own `535`. That reply can only happen if DNS, TCP, the STARTTLS upgrade, real certificate
verification, `EHLO`, mechanism negotiation and the SASL framing all worked — no credential needed. Both
mechanisms pass:

```
535 Username and Password not accepted … BadCredentials …  (auth=plain,   permanent=true)
535 Username and Password not accepted … BadCredentials …  (auth=xoauth2, permanent=true)
```

The XOAUTH2 case is the load-bearing one: a mechanism Gmail did *not* advertise would fail as
`UnsupportedAuthMechanism`, never as `535`. The only untested link left is whether a **real** credential is
accepted, which no test can own.

## Known gaps (stated, not hidden)

- **No containerised TLS test.** Real TLS is now proven against Gmail (above), but the scope's
  docker-compose-gated relay test — which would cover implicit TLS on 465 and a self-signed chain — is
  still owed.
- **The invite link is relative** (`/accept?token=…`) — it was before this slice too. In a mail client
  that is not clickable. A host can already fix it per workspace via a catalog override
  (`message.set_catalog`), which is the honest answer for now; a node-level public base URL is a separate
  small ask that touches `invite_create`, not the transport.
- **Double-send has an irreducible window.** A crash between "the relay accepted" and "the marker is
  committed" duplicates on retry. Two mitigations (marker + stable `Message-ID`), neither exactly-once.
- **Postmark is unexercised against the real API** — its config validation and error classification are
  tested, the wire is not (it is a true external, and the fake-vs-real line here is the provider's HTTP
  API).
